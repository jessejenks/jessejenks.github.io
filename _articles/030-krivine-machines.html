But instead of integers and arithmetic operations, we somehow need to encode the more abstract lambda calculus. In this post, we will explore two abstract machines implementing each strategy.

Krivine's Original Machine

The Krivine machine is an {% include footnotes/link id="krivine-writeup" content="abstract stack machine" %}, named for {% include link href="https://www.irif.fr/~krivine/" content="Jean-Louis Krivine" %}, that implements the call-by-name strategy.

The rest of this post is dedicated to interpreting what is actually happening. Try running a program and seeing it in action first.

de Bruijn revisited


    

        I first introduced de Bruijn indices in the context of let expressions, but this term really comes from lambda calculus. It's very similar, instead of the number of let bindings, it's the number of lambda bindings. Actually, it's not just similar, it's the same thing, because let x = e in b is {% include footnotes/link id="let-derived-form" content="just shorthand" %} for (λx.b) e!
    




    

        And for nested lambda expressions.
    




    

        It's common to see lambda terms written with no variable names at all. For example, λ 0 (λ 0 1). But I prefer the notation λ. #0 (λ. #0 #1) to make the indices extra clear.
    


    

        We get the same benefits as before, it's unambiguous which variable is associated with which binder, and {% include footnotes/link id="de-bruijn-benefits" content="it makes looking up values in a stack easy too" %}.
    






    
Compilation


    

        The compilation scheme is remarkably simple, with only 3 instructions, Access, Push, and Grab corresponding to the three kinds of terms of the lambda calculus. We've already seen Access, in fact it has the exact same scheme as our last stack machine! Push, however, is quite different. Instead of pushing a number, we push entire compiled expressions.
    




        

            Let's work through a simple example: λx.x (or λ.#0).
        




        

            While the derivation is straightforward in this case, things get more complicated when there are applications, because of the nested instructions in Push.
            And, as written, the rule flips argument and caller ordering, which can also be confusing.
        



        
For instance, in just a slightly more complex example ((λf.λx.f x) (λy.y)) (λz.z) (or ((λ.λ.#1 #0) (λ.#0)) (λ.#0)).




    

        Where do these rules come from? One hint is that the outermost instructions (Push, Push, Grab, Grab, Push, Access) correspond exactly to
        {% include footnotes/link id="head-spine-rib" content="the “head spine” of the term, and each Push contains the head spine of the “ribs”" %}. And these are exactly the terms we need in order to perform call-by-name reductions.
    


    

        I prefer to flatten everything by giving each instruction a number, and having the the Push instruction refer the number of the first instruction it contains, rather than actually storing a tree of instructions. This is more convenient for implementation, but it also makes the underlying structure more apparent. We'll use the notation @9 to indicate instruction number 9, so Push(@9) means “push the instructions starting from instruction number 9”.
    




    

        Notice that instructions 0-5 are our original outer-most instructions, and each sub-tree of a Push appears later.
    


    

        This is the flat representation you'll see in the demo.
    






    
Execution


    

        Like the stack machine from the first post, we have two stacks, an environment and a value stack.
        The simplest is the Grab instruction, which is roughly our old Bind. It pops a value off of the stack, and pushes it onto the environment.
    


    

        Our execution completes, not when we reach the end of our instructions, but when we reach a Grab instruction with an empty stack.
    


    

        What are our values? Since we're not computing arithmetic expressions anymore, they aren't just numbers. So what do we actually put on the stack?
    


    

        Given that our push instructions look like Push(@3), our first instinct might be to just push the 3, meaning something like “push the block of code held by this Push instruction”
    


    

        But that's not enough information. We also need to capture the environment when the push occurred.
        The code together with an environment is called a closure.
    


    

        The reason we need to capture the environment is because Access(#0) is relative. If the environment changes before evaluating the access, we'll read the wrong value.
    


    

        For our purposes, a closure is just a pair with an instruction and an environment stack. For instance (@3, []), with an empty environment, or (@7, [(@9, [])]) with an environment containing a single closure, (@9, []).
    


    

        Finally, the trickiest is Access.
        Our previous Access was non-destructive. Access(#3) just meant copy the value at index 3 from the environment into the value stack. This time, we actually change the environment.
    


    

        Let's see a concrete example, Suppose our machine is in the following state, where we are about to execute Access(#1).
    




    

        First, we access #1 in the environment, (@7, [(@9, [])])
    


    

        Now we replace the current environment with the environment held in the closure, [(@9, [])].
    




    

        Finally, we jump to the instruction held in the closure, @7.
    




    

        That was all in a single instruction!
    


    

        In summary
    











    
Tweaking the Machine for CBV


    

        The next machine implements a call-by-value strategy. Surprisingly, it is nearly identical to the first Krivine machine. In fact Leroy simply calls it {% include footnotes/link id="marked-krivine-presentation" content="“Krivine's machine with marks on the stack”" %}.

        The previous machine delayed evaluation of arguments in applications by pushing them onto the stack to be grabbed and accessed at some later point. If the value is never accessed, it is simply never evaluated.
    


    

        So, to get call-by-value, we just need to avoid deferring the values. Seems simple enough, just immediately execute the code for the argument before moving on to the caller. But this alone does not work. We need to somehow keep track of where to return to, once we are done evaluating the argument.
    


    

        To do this, we can “mark” a closure, which we'll indicate with an exclamation point, like (!@3, []). The mark will mean “return to this location”.
    


    

        The compilation scheme for our new machine is exactly the same. But, we'll use the name Reduce instead of Push, since we now reduce arguments first.
    




    

        The behavior of Access is also unchanged. The real difference is in how Reduce works, and how Grab treats marked vs. unmarked closures.
    


    

        
        If instruction n is Reduce(@m), we push a marked closure (!@n+1, e) onto the stack, and immediately jump to m. In other words, push a closure that starts from the next instruction after the Reduce.
    


    

        Grab is like a dual instruction to Push. And with marked closures, it acts like a dual to Reduce.
        When we see an unmarked closure, we move the closure from the stack to the environment.
        But when we see a marked closure, we return to that location.
    








    
Arithmetic


    

        As we noted, our let expressions from the first post are secretly just lambda expressions. So let x = N in M is shorthand for (λx. M) N.
    


    

        Let's compare how these get compiled in the arithmetic stack machines and in our marked Krivine machine.
    




    

        The arithmetic machine compiles and evaluates expressions in the same order that the marked Krivine machine does! So our choice to avoid recomputing expressions with let was call-by-value all along.
